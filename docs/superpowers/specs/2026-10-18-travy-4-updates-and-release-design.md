# «Травы», план 4: обновление базы по сети и выпуск APK — дизайн

Дата: 2026-10-18
Основа: спецификация `2026-10-15-travy-design.md`, §4.3, §7, §10, §11, §12. Этот документ уточняет их и не противоречит им, кроме отмеченных мест.

## 1. Зачем

Довести справочник до состояния, в котором его можно раздать близким: APK по ссылке, база трав обновляется сама, без переустановки. Это последний шаг перед переходом к большому продукту «Травница» (сообщество + дневник), поэтому решения сейчас не должны мешать потом добавить аккаунты и сервер.

## 2. Решения пользователя

| Вопрос | Решение |
|---|---|
| Платформа выпуска | Только Android (APK). iPhone — позже, вместе с «Травницей» (App Store) |
| Где собирать APK | В облаке Expo (EAS Build, бесплатный тариф) |
| Распространение | GitHub Releases, ссылка близким (спецификация §12) |
| Обновление базы | Как в спецификации §7: с GitHub Pages, раз в сутки + вручную |

## 3. Цели и не-цели

**Цели**
- Обновление базы по сети по §7: проверка, скачивание, проверка целостности и схемы, атомарная замена, обновление на лету без перезапуска, фото в фоне, уборка неиспользуемых фото.
- Экран «О приложении»: версия приложения и базы, кнопка «Проверить обновления» с понятным результатом.
- Уведомление «База обновлена: +N трав, изменено M».
- Устойчивость к исчезновению данных после обновления: фильтры и избранное не ломаются, если трава или запись словаря пропала из базы.
- Готовое к сборке приложение: идентификатор, номер версии, своя иконка и заставка, `eas.json` с профилем `preview` → `.apk`.
- Инструкция выпуска: от `npm run content:app` до ссылки в GitHub Releases.

**Не-цели**
- iPhone, App Store, Google Play, веб-версия.
- Обновление кода приложения по воздуху (EAS Update) — код обновляется новым APK (§7).
- Аккаунты, сервер, синхронизация.
- Автоматическая выкладка APK в Releases из CI (нужен токен Expo в секретах — лишняя сложность для редких выпусков).

**Анти-цели (провал, даже если «работает»)**
- Обновление может испортить базу или пользовательские данные: после любой ошибки на любом шаге приложение продолжает работать на прежней базе.
- Приложение без сети показывает ошибки или тормозит на старте.
- Обновление молча откатывает базу назад (например, новый APK со свежей встроенной базой не должен уступать более старой скачанной).

## 4. Как устроено

### 4.1. Где живёт логика

- **`shared/src/update/`** — весь алгоритм обновления как чистый TypeScript без Expo и Node: шаги §7 работают через внедряемые зависимости (загрузка по сети, хранилище, sha256, время). Тесты — Vitest с подменой сети и хранилища, все случаи из §11: новая версия, та же версия, битый sha256, неверный размер, невалидный JSON, ошибка схемы, несовместимый `schemaVersion`, офлайн, таймаут, частичный провал фото, уборка старых фото, встроенная база новее скачанной.
- Там же — сводка изменений (`+N трав, изменено M`: новые id, удалённые id, изменённые — по сравнению JSON записей) и «очистка» фильтра от id, которых нет в текущей базе.
- **`app/`** — тонкие адаптеры: `ContentStore` на `expo-file-system`, sha256 на `expo-crypto`, загрузка через `fetch` с `AbortSignal`-таймаутом, состояние проверки в `AsyncStorage`.

### 4.2. Хранилище (`ContentStore`, спецификация §4.3)

Папка документов приложения:

```
content/
  active.json      активная скачанная база (content.json целиком)
  incoming.json    временный файл во время загрузки
photos/
  <sha256>.webp    скачанные фото
```

Интерфейс: прочитать активную базу; записать временную; сделать временную активной (переименование); удалить временную; список скачанных фото; записать фото (через временный файл); удалить фото. Веб-реализация не делается (не-цель), но интерфейс её допускает.

### 4.3. Какая база активна при запуске

1. Читается встроенная база (как сейчас).
2. Если есть `active.json` и его `contentVersion` больше встроенной и `schemaVersion` совпадает с поддерживаемой — он разбирается схемой и становится активным. Любая ошибка чтения/разбора → встроенная база, файл удаляется.
3. Если встроенная новее или равна скачанной (поставили новый APK) — скачанная база и ставшие ненужными фото удаляются.

Список скачанных фото читается при запуске один раз и держится в памяти; `photoSource(path)` ищет сначала скачанное (`{ uri }`), затем встроенное, иначе `null` (заглушка уже есть).

### 4.4. Проверка обновлений

- **Когда:** при запуске и при возврате приложения на передний план, если с прошлой *успешной* проверки прошло ≥ 24 ч; вручную — кнопкой в «О приложении» (без ограничения по времени). Одновременно идёт не больше одной проверки.
- **Адрес:** `https://niyazabuy.github.io/travi/` — одна константа в коде приложения.
- **Шаги:** ровно §7. Таймаут манифеста 10 с; `content.json` — 60 с; каждое фото — 30 с.
- **Проверка скачанной базы:** размер и sha256 совпадают с манифестом → JSON → нестрогая схема бандла из `shared` → `schemaVersion` и `contentVersion` совпадают с манифестом. Ссылочная целостность (все id, на которые ссылаются травы, существуют) — тоже проверяется: экраны рассчитывают, что ссылки ведут на существующие записи. *(Уточнение §7.4.)*
- **Применение:** переименование `incoming.json` → `active.json`, затем в памяти подменяется контент (`ContentProvider` становится заменяемым), открытые экраны перерисовываются.
- **Фото:** после применения базы — фоном по одному те, которых нет ни во встроенных, ни в скачанных; каждое проверяется по sha256 и пишется через временный файл. Ошибка одного фото не останавливает остальные. После успешной докачки — удаление скачанных фото, на которые активная база больше не ссылается. Недокачанные фото докачиваются при следующей проверке, даже если версия базы не изменилась.
- **Что считается проверкой для 24-часового таймера** *(решение Claude)*: проверка «завершена», если манифест получен и по нему принято решение — база актуальна, применена, отвергнута (битый sha256/размер/схема) или нужна новая версия приложения. Только тогда запоминается время. Нет сети / таймаут / ошибка HTTP на манифесте → время не запоминается, следующая попытка — при следующем запуске или возврате в приложение. Провал отдельных фото не мешает завершению; недокачанные фото пробуются при следующей завершённой проверке (через сутки или вручную). Отвергнутая база пробуется снова тоже через сутки.
- **Схема не прочиталась при верном sha256** — это почти наверняка новый формат, который забыли отметить увеличением `schemaVersion`. Сообщение то же, что для несовместимой схемы: «Доступна новая база — обновите приложение». Защита от этого уже есть: охранный тест `shared/test/compat.test.ts` ломает CI, если перечисления изменились без `SCHEMA_VERSION`.
- **Состояние** (`AsyncStorage`, ключ `travy.update.v1`): время последней завершённой проверки; флаг «есть база новее, но нужно новое приложение» с версией схемы. Нечитаемое состояние = пустое.

### 4.5. Что видит пользователь

- **Автоматическая проверка:** без сети, ошибок и «база актуальна» — ничего. После применения — всплывающая плашка внизу на ~4 с: «База обновлена: +2 травы, изменено 3» (склонения через `countRu`). Если по травам и сборам ничего не изменилось (поменялись только словари/источники) — «База обновлена»; если не изменилось вообще ничего, кроме версии, — база применяется молча.
- **«О приложении»:** версия приложения (из `app.json`), версия и дата базы, «скачана из сети» или «встроенная», кнопка «Проверить обновления». Результат ручной проверки — текстом под кнопкой: «Проверяю…» / «База актуальна» / «База обновлена: …» / «Нет связи с сервером, попробуйте позже» / «Скачанная база повреждена, оставлена текущая» / «Доступна новая база — обновите приложение». Строка «Обновление базы по сети появится в следующей версии» убирается.
- **Пропавшие записи:** в списке трав фильтры, ссылающиеся на исчезнувшие id, тихо выбрасываются; трава из избранного, исчезнувшая из базы, показывается как сейчас («Трава удалена из базы»).

### 4.6. Версия базы без лишних перезагрузок *(решение Claude, уточнение §5.7)*

Сейчас `contentVersion` — время сборки. Поэтому база, встроенная в APK, всегда «старше» той, что CI соберёт из того же коммита минутой позже, и каждый свежий APK сразу скачивает ту же самую базу. Исправление:

- `contentVersion` = время (UTC, `YYYYMMDDHHmm`) последнего git-коммита, затронувшего `content/`. Одинаковое содержимое → одинаковая версия и на компьютере, и в CI.
- Если в `content/` есть незакоммиченные изменения или git недоступен — текущее время (как сейчас; так работает разработка).
- CI: `actions/checkout` с `fetch-depth: 0`, чтобы история была доступна.
- Следствие: изменение только кода сборщика (например, сжатия фото) без правки `content/` не выпускает новую версию базы. Чтобы выпустить — нужна любая правка в `content/`. Записать это в `docs/release.md`.
- Вторая страховка — молчаливое применение без изменений (§4.5).

### 4.7. Подготовка к сборке

- `app.json`: `android.package` = `io.github.niyazabuy.travy` *(решение Claude: нейтральный идентификатор, не мешает будущему переименованию в «Травницу» — название на экране меняется свободно, идентификатор — никогда)*; `android.versionCode` = 1, `version` = `1.0.0`; разрешение на интернет (есть по умолчанию).
- Иконка и заставка: свои, вместо стандартных Expo — светло-зелёный (`#9BD49B`) лист на тёмном лесном фоне (`#0B120E`); генерируются скриптом из SVG через `sharp` (уже есть в `tools`), PNG коммитятся. Адаптивная иконка Android (передний план, фон, монохромная) + `icon.png` + `splash-icon.png` + `favicon.png`.
- `app/eas.json`: профиль `preview` — `android.buildType: apk`, `distribution: internal`. Сборка из монорепо (npm workspaces) — проверить, что EAS ставит `@travy/shared`.
- Удаляются шаблонные картинки Expo, которые больше нигде не используются.

### 4.8. Выпуск

План заканчивается первой настоящей сборкой: всё до неё Claude делает сам, затем пользователь входит в Expo, Claude запускает облачную сборку, пользователь ставит APK на свой телефон и проверяет, после чего создаётся релиз.

Документ `docs/release.md`:
1. `npm run content:app` (встроенная база = свежая), тесты, коммит, пуш.
2. `cd app && npx eas-cli build -p android --profile preview` (первый раз — `npx eas-cli login` и согласие создать ключ подписи; это делает пользователь сам).
3. Скачать `.apk` по ссылке из вывода EAS, переименовать в `travy-<version>.apk`.
4. GitHub → Releases → «Draft a new release», тег `v<version>`, приложить APK, опубликовать.
5. Перед следующим выпуском — увеличить `version` и `versionCode`.

Ключ подписи хранит Expo; потеря доступа к аккаунту Expo = новые версии не встанут поверх старых. В документе — как скачать резервную копию ключа (`eas credentials`).

## 5. Что остаётся на усмотрение исполнителя

- Разбиение `shared/src/update/` на модули, имена функций и типов.
- Вид всплывающей плашки (в рамках темы).
- Конкретный рисунок листа в иконке.
- Как именно `ContentProvider` подменяет контент (контекст со state, ref и т. п.), при условии что все экраны видят новую базу без перезапуска.

## 6. Что понадобится от пользователя

- Аккаунт на expo.dev и вход `npx eas-cli login` — перед первой сборкой.
- Проверка APK на своём Android-телефоне до раздачи близким.
- Создание релиза на GitHub (или разрешение Claude сделать это через `gh`, если он будет установлен и авторизован).
